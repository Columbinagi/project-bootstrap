# 回头对齐 — 把已有项目拉到当前规范

> **仅在用户明确要求时执行**（例如"把 X 项目按规范对齐"、"给这个项目补上规矩"）。**不自动触发。**
> 用户只是聊到文件夹结构时，**不要**启动本清单，也不要建任何文件。

**三个入口，同一套流程、同一个主出口：**

| 入口 | 重点 | 走到哪 |
|---|---|---|
| **有规矩，但过时 / 与实际做法对不上** | **比对差异、改结构** | 第 0 步取证 → 第 0.5 / 1 步 → 第 2–5 步（**审一次 → 一次改到位**） |
| **没规矩，但有已发生的历史**（项目已在跑） | **从事实提炼规矩、补文档** | 第 0 步取证 → 第 0.5 / 1 步 → **第 1.5 步**（补文档）→ **需要时**再走第 2–4 步 |
| **部分有规矩**（骨架文档只建了一部分：如已有 `AGENTS.md` / `MEMORY.md`，缺 `PRD.md` / `CONTRACT.md` / `USER.md`） | **只补缺的文档、不重写已有文档**（补法同第 1.5 步；**目录命名差异照常进单子**，见第 2 步） | 第 0 步取证 → 第 0.5 步（**判该不该补**）→ 第 1 步（**逐条判定缺哪几份**）→ **第 1.5 步补缺** → 需要时再走第 2–4 步 |

### 入口① 最常见的触发：**skill 自己升级了**（项目要不要跟着对齐）

> **这不是第三个场景，也不新开流程** —— 它就是**入口①**：「**规矩过时**」不只指项目自己的规矩过时，
> 也指**它当初依据的 skill 版本过时**（那套口径后来改过）。
> 两条路——**回头对齐**与**一开始就用 skill 建的项目**——**最后都会走到这里**：用久了，skill 升了版，项目要跟一次。

**这一轮的走法（仍是"先只读 → 出单子 → 批一次 → 一次改到位"，只是取证对象换成"版本差"）**：

| # | 步骤 | 判据 / 产出 |
|---|---|---|
| 1 | **报版本号** | 读 `SKILL.md` frontmatter，报**现行版本** |
| 2 | **找项目记的旧版本** | 在项目里找当初的版本号（`AGENTS.md` / `PRD.md` / `MEMORY.md` 里常写着"按 project-bootstrap vX.Y.Z 判定"）；**没记就如实说"没记"**，别猜 |
| 3 | **取版本差** | 读 `references/versions.md` §十一，把「**项目那版 → 现行版**」之间的**每一行**列出来（含【取代】指针 —— 被取代的口径也要能看出"旧说法错在哪"） |
| 4 | **逐条判影响**（这一步是关键） | 每条变更 → **对本项目有没有影响**：**有** → 说明影响哪份文件 / 哪条规矩 / 要不要动产物；**没有** → 写「**不适用**」并给一句理由。**不许整段跳过** |
| 5 | **出单子交批** | 表：**变更 ｜ 影响本项目吗 ｜ 影响什么 ｜ 建议怎么改**；**「执行？」留白**；**改不改由使用者批** |
| 6 | **批了一次改到位** | 同第 4 / 5 步：动过目录就逐个修链接并实测 ＋ 回填评估记录 ＋ 过六条验收 |

> ⚠️ **判"无需对齐"是合法结论，但必须给证据**：那就要**逐条**说明"每条变更为什么对本项目无影响"，
> 不能只说一句"本项目已符合现行规范"。**空清单 ≠ 没干活**（见第 0.5 步）。
>
> ⚠️ **不许顺手升级**：这一轮只做"该不该跟"，**改哪些由使用者批**；没批之前**一个文件都不动**。
> **也不要在项目里写死"必须永远跟到最新版"** —— 跟不跟是使用者的决定，这里只提供"看得清"的取证。


**五个步骤一条线**（口径见 `SKILL.md` 场景二）：

1. **只读取证**（**本文**第 0 步）—— 不改任何文件
2. **定目标形态**（判定题正见 `SKILL.md` 第 0 步；本文第 1.5 步 ① 与第 2 步导语各写一次）—— 定**标准版 / PRO 版**，逐条给判定
3. **出完整差异清单**（**本文**第 0 步 ②）—— **现状 / 建议 / 影响面 / 判定** 四列齐
4. **使用者审一次**（**本文**第 5 步「输出与执行」）—— 整体批准或圈条
5. **一次执行到位**（**本文**第 4 / 5 步）—— 修链接实测 ＋ 回填评估记录

> ⚠️ **这五步是「逻辑链」，不是「章节顺序」** —— 差异清单**在第 0 步 ② 只立骨架**，
> 随 **第 0.5 / 1 / 1.5 / 2 / 3 步**逐项查、逐项落进单子（判定的定义在第 0.5 步）；
> 最后在第 5 步交使用者审。**照章节走与照这五步走是同一件事** —— 括号里的节号允许跳号，
> 不是"另一个顺序"。

**核心纪律：先只读、不动手；产出清单交使用者审一次；调用即整改 ——
主出口永远是「取证 → 整改清单 → 批准 → 改到位」。**

> ### 第一纪律：规矩的权威来源是「已经发生的事实」，不是模板
> 先看清楚**实际是怎么干活的**（目录结构、提交历史、产出物、现有文档），**再**决定该写什么规矩。
> **不要拿模板去套一个规矩** —— 那只会造出一份和现实对不上的契约。

---

## 第 0 步：只读取证，出两张单子

**这一轮不许改任何文件。** 先取证，再谈规矩。

**① 事实清单 —— 这个项目实际上是怎么干活的？**

读：目录结构、`git log`（谁在什么时候动了什么）、产出物、现有文档。
写下：**实际的工作流、约定的落点、已经形成的惯例、明显踩过的坑** ——
以及**线与线之间的接口 / 契约实际写在哪**（内容按什么格式写、工程按什么格式读、谁改谁不许改）。

> **先记一条「进场基线」**（第 0.5 步报事实要用）：**进场时**跑一次 `git status --short --ignored`，
> 把输出**原样记下来**。项目常驻的忽略项（`.trae/` `.workbuddy/` `.venv/` `dist/` `logs/` 这类）
> **进场就在，不是本次改动** —— 有了基线，跑完才能"只比差异"。

**② 差异清单 —— 现有文档 / 命名 / 目录和规范差在哪？**

项目还没有骨架文档时，这一项为空 —— 继续走 **第 0.5 步（判"要不要补"）→ 第 1 步（缺哪几份）→ 第 1.5 步（怎么补）**。
**骨架文档只有一部分时，这一项不为空** —— 缺的那几份本身就是差异项，照样走第 1.5 步（补缺、不动已有）。

| # | 项 | 现状 | 建议 | 影响面 | **判定** | 执行？ |
|---|---|---|---|---|---|---|

- `影响面`：**若项目已对外分享**，写清会不会断链 / 让已分享的旧链接失效；
  **未分享就写「当前无外部链接」** —— **不要套一句在本项目里不成立的空话**。
- `判定`：**执行方的建议判断** —— **缺陷** ／ **另一种合理选择（不改）** ／ **不适用**（定义见第 0.5 步）。
  **进了这张单子就要给判定**（理由可短，但不能空）。
- `执行？`：**留白** —— 由**使用者**在批复时填（改成"改"或圈掉）；**执行方不预填**。

> **必填列**：`项`（每行的主语）/ `现状` / `建议` / `影响面` / `判定` —— 少一列这张单子就没法审（其余列可选）。
> **清单不是一次写完的**：第 0 步只立骨架，**随第 0.5 / 1 / 1.5 / 2 / 3 步逐项补**，第 5 步整张交审。

> **表可以按项目情况扩列 / 改分组**（结构类是默认值）—— 但**第 0.5 步要的「判定」维度必须在**：
> 既不禁止适配，也不许丢维度。

> ⚠️ **知情者偏差（先自查）**：若**你本人就是这个项目的长期参与者**（上下文里已装了大量项目知识），
> 你的盘点会天然偏向「**每项都不需要改**」—— **你看得懂，所以不觉得缺什么**。
> 此时必须**额外问自己一遍**：**一个新人只读这些文档与 git 历史，接得上手吗？**
> 接不上 → 那是**缺陷**，不是"另一种合理选择"。

> **盘点不设范围上限**：读得越透越好 —— 发现「**文档说的 ≠ 实际做的**」是**加分**，不是越界。
> 唯一的护栏是：**只读**（不改任何文件）＋ 结论**交使用者审一次**。

## 第 0.5 步：先判「该不该动」，再谈「怎么动」

**盘点完了，不要直接进入"改"。先对每一项回答一个问题：**

> 这条差异是「**缺陷**」，还是「**另一种合理选择**」？

| 判定 | 处理 |
|---|---|
| **缺陷** —— 会造成实际损害（断链、规则打架、误导后来者） | 进入后面的流程 |
| **另一种合理选择** —— 只是和模板不一样，但自洽且能用 | **明确写「本项判定不需要改」并给出理由，同样算完成** |

> **判断提示 —— 看规矩的「来源」**：
> **项目自己长出来的**（做法先成型、后成文）→ 差异多半是「**另一种合理选择**」；
> **外来模板套上的**（先有模板、再要求现实符合它）→ 差异多半是「**缺陷**」。
> 这只是**先验**，不是结论 —— 仍要逐项按上表判。

> ⚠️ **两类不适用本表**（它们是**硬规则**，没有"另一种合理选择"）：
> ① **骨架层命名不合规**（成分表里的目录名是中文 / 同层中英混搭 / 数字前缀）→ **零豁免**，一律列缺陷、建议改英文（见第 2 步；**改不改仍由使用者批**）；
> ② **产物放错地方**（根目录住着产物、由源生成的成品没进 `dist/`、`release/` 被 AI 代刷）→ 见 `versions.md` §八，**全项目只有一种放法**。
>
> **不在管辖内的**：**骨架目录内部**的子目录与文件结构（`content/` 里怎么分、`docs/` 下怎么组织、用什么语言）—— **由项目自己定**，**不列缺陷**（只可作"非骨架层"的建议，改不改由使用者批）。

**这一步对「补」同样适用**：项目缺某份文档，也先问一句「**缺了它，实际造成损害了吗？**」
—— 若项目已自行长出等效机制，**判定「不需要补」同样算完成**（写清理由即可）。

> ⚠️ **唯一例外是 `PRD.md`** —— 它承担「变更的比较基准」这一职能，别的文档替代不了（见第 1 步）。
> 缺 PRD 的项目，**判定是"要补"**，只是补法用历史反推（第 1.5 步）。

**核心纪律：调用即整改 —— 主出口永远是「取证 → 整改清单 → 批准 → 改到位」。**

> **差异清单为空**，只是「**这个项目本来合规**」的**如实陈述**，**不是流程的设计目标**；
> 流程**不会为了"改点什么"而制造改动** —— 该改的按清单改到位，不该改的写明理由，**两者都要留痕**。

> ### 判断与事实要分开报（**别把判断当取证**）
>
> | 要报的东西 | 是什么 | 怎么核 |
> |---|---|---|
> | **判定** | 一个**判断** —— 这一项要不要改（判"不需要改"也要给理由） | 是结论，**不由某条命令"证明"** |
> | **事实：无跟踪文件被改** | 没有**跟踪文件**被改 | `git status --short` 里**除 `??`（未跟踪新文件）外，任何状态位非空都算被改**：`M` / `A` / `D` / `R` / `C` / `U` / `T` 任一列的字母都算 —— **只看 ` M` 会漏判已暂存的改动（`M ` `MM` `A `）与改名 / 删除（`R ` `D `）** |
> | **事实：无未登记的增删改** | 无跟踪文件被改 ＋ 无新增未跟踪文件 ＋ **无本次新增的被忽略文件** | `git status --short --ignored`（**必须带 `--ignored`**，否则看不见 `logs/` `dist/` 这类被忽略的落点），**与第 0 步记下的「进场基线」逐行对照、只比差异** |
>
> ⚠️ **别指望这条输出"完全为空"**：项目常驻的忽略目录（`.trae/` `.workbuddy/` `.venv/` `dist/` `logs/` …）
> **进场就在**，`--ignored` 会一直列着它们 —— **"有常驻忽略项"不是"有增删改"**。
> 判据是**与进场基线有无差异**，不是"输出是否为空"。
>
> ⚠️ **不许用 `git diff --stat` 去"实证没有改动"** —— 它**看不见未跟踪文件**，证不了"没有新增"。
> 要说事实，就用 `git status --short --ignored`，**并对照进场基线**。
>
> **结论要写清两层**：判定（各项要不要改）＋ 事实（如「无跟踪文件被改」／「另有 **N 个新增文件**」）。
> **本轮有落盘或新增时，事实层不许简写成"没有改动"。**

> **留痕不是可选项**：把它**列进差异清单的"待办"里一起点头**，**不要为它单独再问一轮**。
> 落点**优先用项目已有的进度文件**（没有才是 `MEMORY.md`）。

## 第 1 步：骨架文档齐不齐

| 应有 | 检查什么 |
|---|---|
| `AGENTS.md` | 是否存在；是否含**「产物长出来的顺序」表**、**写入规范**与**形态结论** |
| `MEMORY.md` | 是否存在；是否**按日期累积**（最新在上） |
| `PRD.md` | 是否存在；是否含**「前提假设」**一节 |
| 接口 / 契约 | 有没有**线间接口**（内容线与工程线之间的字段 / 格式约定）？写在哪、**是否只写一处**、变更登记在哪（见 `versions.md` §十）—— **单线项目判「不适用」** |
| `ROADMAP.md` | 是否存在；是否有关卡与**当前唯一卡点** |
| `SOUL.md` | 是否存在；是否为协作准则（**按线**并准则附录：内容线＝写作纪律 / 代码线＝编码准则，见 `versions.md` §一.2） |
| `USER.md` | 是否存在；是否含**项目默认根目录**（**新建项目适用**；已有固定位置的老项目可判「不适用」） |
| `ACCEPTANCE.md` | **只有进入验收前**才该有（＝交付物已齐、准备逐条对 `PRD.md` §六验收基准）；早建即冗余 |

> **逐条给判定，不许跳过任何一行** —— 每条要么进"建议改"，要么写明「**不需要改**」或「**不适用**」并给理由。
> **默默跳过 ＝ 漏检**，而且事后看不出来是"判过了"还是"漏了"。
> 长清单尤其容易悄悄少一条 —— 交单子前**回数一遍行数**。

**判据分两用 —— 混用会误删文档：**

| 用在什么事上 | 判据 |
|---|---|
| 决定**该不该新写**一份 | 「**它回答的问题，别的文档回答不了吗？**」—— 回答得了，就别新建 |
| 决定**已存在的要不要删 / 合并** | 「**它承担的职能，别的文档承担得了吗？**」—— **这是更高的门槛** |

> ⚠️ **不要拿前一条去删已有文档。** 「**内容被别处覆盖**」**不等于**「**职能可以被替代**」——
> 基准类文档尤其如此：基准的第一要求是**单一、稳定、可对照**，散在三处 **= 没有基准**。
> **`PRD.md` 默认不删、不并**（判据与理由见 `versions.md` §十）。

## 第 1.5 步：项目没有骨架文档（**或只有一部分**）时 —— 是「补」，不是「改」

> 项目**已经在跑**，但没有契约 / 进度 / 结论三类文档 —— 这是最常见的入口。
> **只有一部分时走同一条路**：**只补缺的文档，已有的不重写、不"顺便规范化"** ——
> 补哪几份由第 1 步逐条判定给出，**不因为"缺了"就把已有的也重做一遍**。
> **注意范围**：这只管**文档** —— **目录命名这类差异照常列进单子**（见第 2 步），"不重写已有文档"不等于"目录也不许动"。
> **不要把主流程（`SKILL.md` 第 0–7 步）重走一遍**，也不要从"建项目文件夹"开始重来。
> 走法：**从已发生的历史里反推规矩。**

1. **判形态**（`SKILL.md` 第 0 步 —— **一道判定题**）：这个项目是不是**双主业**（持续积累的内容源 ＋ 自维护的加工工具）？
   是 → **PRO 版**；只有一类主业 → **标准版**。**与人员分工无关**；代码放哪**不算判定题**（按角色归位：`src/` `tests/` / `scripts/` / `engineering/`）
   - **同时先读 Agent 侧已有的全局约定**（全局自定义指令 / 全局配置文件）。
     **已经写过的不要在这里再写一遍**（例：全局已有完整编码准则，`SOUL.md` 就不必再并一份）——
     两份正文 ＝ 第二处要同步的地方。
2. **建议补哪几份，写进差异清单** —— **不另开一道审**：这就是第 0 步 ② 那张单子的补档部分，
   在第 5 步**随整张单子一次交使用者批**；批完**一次写完**，不要一份一份挤牙膏。
   （只列"补哪几份 ＋ 依据"，**不要闷头一次建齐** —— 见 `SKILL.md` 场景二纪律 3）
3. **按事实清单写 `AGENTS.md`**：把第 0 步看到的**实际做法**写下来（目录怎么分、东西放哪、命名怎么起的、踩过什么坑），
   **＋ 一句话形态结论**（`SKILL.md` 第 0 步 —— 这是**硬要求**，下次会话的 Agent 靠它读形态），
   **＋ 「产物长出来的顺序」表**（从 `versions.md` §四 **原样抄**，**已建标 `☑`、未建标 `☐`**）——
   **这张表是"按需生长"在项目里的落点**：以后每次会话的 Agent 靠它自查（见该表末尾的「Agent 义务」），
   **缺了它，项目就只剩"当前长什么样"，没有"什么时候该长什么"**，
   **不要写"我们希望以后怎么做"** —— 契约要对上现实
4. 补 `MEMORY.md`（从 `git log` / 产出物回填关键决策与当前状态）、`USER.md`（现问）、
   `SOUL.md`（协作准则 ＋ **按线**并准则附录：内容线＝写作纪律 / 代码线＝编码准则）
5. **补 `PRD.md` —— 用历史反推**：目标、硬性约束、**前提假设**、验收基准，从**已经做过的事**里提炼。
   > ⚠️ **"不用从零写" ≠ "不用写"。** PRD 是变更的比较基准，缺了它，往后所有改动都没有对照物。
   > 区别只在**素材来源是历史**，不是空白纸。
   > **接口 / 契约也算 PRD 的职能域**：把历史里**实际在用的**字段 / 格式约定找出来写进 `PRD.md` 对应节，
   > 或独立成 `CONTRACT.md` ＋ `PRD.md` 留指针；**变更记录仍归 `PRD.md`**（`versions.md` §十）。
6. **已有等效机制就不要强改**（项目自带的入口文件 ＋ 进度文件 ＋ 记录已能顶事）——
   按 `SKILL.md` 开头的「默认结构，不是强制结构」，**补差异，不改形状**
7. **不重排目录** —— 补规矩不是趁机大扫除。**但"不重排"≠"不许列入单子"**：目录命名（第 2 步）这类差异
   照常进单子，**由使用者审一次、按批复一次改到位**，动了目录就按第 4 步修链接
8. `ROADMAP.md` 仍**等 PRD 审核通过**再写；补完把结果回填一条到 `MEMORY.md`

## 第 2 步：目录名与落点是否合规（**拿 §三 成分表逐项对**）

> **先定目标形态，再谈名字** —— 形态（标准版 / PRO 版）决定**该不该有 `content/` `engineering/`**；
> 命名**只管「骨架层」**：**成分表里的目录名**用**英文小写**（`versions.md` §三 命名规则 / §六 第 4 条）—— 这是**硬规则（零豁免）**，
> 骨架层不合规的一律**列缺陷项、建议改英文**；**改不改由使用者批**（见本节末）。
> **骨架目录内部**（`content/` 里怎么分、`docs/` 下怎么组织、用什么语言与文件命名）**由项目自己定** —— **不看不列**。

**命名语言只有一条规则**（定义见 `versions.md` §三；执行口径本节）：
**骨架层目录英文小写、根目录骨架文档英文大写**；**骨架目录内部（子目录与文件命名、语言）由项目自己定**。
**目录不是"按某个维度切出来"的** —— 而是从 `versions.md` §三 **一张成分表里按需长出来**：
**先在成分表里取，表里没有的才造词并登记**。

**中文目录名对号入座**（改名**逐个来**，改完统一登记进 `AGENTS.md` 的「产物长出来的顺序」表；**新增**目录仍按「一次只加一个」）：

| 现状（中文名是事实，不是规范） | 规范 |
|---|---|
| `内容/` `内容区/` | `content/` |
| `工程/` `工程区/` | `engineering/` |
| `技能/` | `skills/` |
| `计划/` | `docs/plans/` |
| `发布/` | `release/` |
| `资料/` | `docs/references/` |

> **名字本身就是权限边界**，所以改的时候按三条走：① 归属一眼可辨；② **逐个改**，改完按第 4 步
> 逐个修链接并实测可达 —— **断链是这一步要修的活，不是不做的理由**；③ 目录名与 `AGENTS.md` 里写的工作线一一对应。
>
> **其他目录**：拿 `versions.md` §三 的**成分表**逐项对。
>
> **真正该动的三类**（**都指骨架层**）：① 名字**误导归属或造成混用**（数字前缀、同层中英混搭、`产出物/` 这类指代不清）；
> ② **中文目录名**（**零豁免** —— 一律列缺陷、建议改英文）；③ 内容**确实该换落点**（图件混在文档目录里之类）。

> **骨架层命名不设任何例外（零豁免）** —— **成分表里的目录名**若是中文 / 同层中英混搭 / 数字前缀，
> **一律列为差异项、建议改英文**。
> **不接受任何形式的模糊豁免**：文件注释、脚本里的说明、别的文档、口头约定，
> 以及"这一摊归谁管、所以可以用中文"这类**推断** —— **都不构成理由**。
> **骨架目录内部不作缺陷**：里面的子目录与文件结构（含语言）**由项目自己定** —— **不列缺陷项**；
> 确有问题（一类东西散在三处、层级过深、留 `misc/` 兜底）也只写成**建议**，**标明"非骨架层，仅供参考"**，
> **改不改由使用者批**（方向见 `versions.md` §三.3）。
> **唯一的出口在使用者手上**：他**当轮拍板**说"这个项目就用中文名" → 那是**他的决定**，
> 按他的决定记入 `AGENTS.md`，并在单子上写明"**由使用者决定**"；**没批就不动**。

> **零豁免 ≠ 可以自行改名** —— 判定一律是"缺陷、建议改英文"，但**执行仍要使用者批**：
> 逐项进单子，**没批就不动**。与第 1.5 步第 7 条「不重排目录」的关系：那条管的是**不擅自大扫除**，
> **不是不许列入单子**。

| 旧（指代不清 / 混搭） | 新（规范） |
|---|---|
| `10_xxx` `20_xxx` `30_xxx` 之类**数字前缀**、同层中英混搭 | 名称**指代清楚** ＋ **英文小写**；按 §三 成分表取 `docs/` `assets/` `models/` `notes/` `archive/` `logs/` |
| **中文目录名（骨架层）** | 翻成对应工作线的**英文小写**名（见上表）—— **零豁免**：一律列缺陷、建议改英文；**改不改由使用者批** |
| 骨架目录**内部**的中文子目录 / 文件名 | **不算缺陷**；只可列为**建议**（标明"非骨架层，仅供参考"），改不改由使用者批 |
| `历史版本/` `旧版/` | `archive/`，**或直接交给 git**（见下） |
| `产出物/` `交付物/` | `docs/`（手写即交付）／ `dist/`（由源生成）／ `assets/` `models/`（图件 / 模型） |

**`archive/` 与 git 的分工**：git 保存所有历史；`archive/` 只放**不再维护但仍需被人一眼翻到**的东西。
> **纯历史版本不必另存文件** —— 直接删，要用时从 git 取。

## 第 3 步：目录内容是否混放

| 检查 | 判据 |
|---|---|
| `models/` 与 `assets/` 是否混放 | 模型**本体**进 `models/`；**被文档引用的图件**进 `assets/`；一个文件只放一处 |
| `notes/` 里是否有本该进 `MEMORY.md` 的短结论 | 短结论（索引）进 `MEMORY.md`；长论证进 `notes/` |
| `notes/` 里两类文件是否混了 | 任务结论 `{任务名}_结论_{YYYYMMDD}.md` 可**同主题续更**；分析文档 `{YYYYMMDD}_{子主题}.md` **只增不改** |
| `logs/` 是否存在、临时文件是否乱落 | 临时文件一律进 `logs/`（已被 `.gitignore` 排除） |
| **根目录是否住着产物** | **根目录只住骨架文档、`README.md`（按需门面）与 `.gitignore`**；产物按 `versions.md` §八 落位：手写即交付 → `docs/`；由源生成 → `dist/` |
| `dist/` 的产物是否被手改、有没有生成入口 | 产物**勿手改** —— 要改回源头（`content/` 或 `src/` 与 `templates/`）重新生成；**找不到生成入口的 `dist/` 文件 = 缺陷** |
| `release/` 是不是 AI 代复制 / 代刷新的 | `release/` 只由**使用者手动**从 `dist/` 复制定版；**AI 不代劳** |
| 有 `engineering/` 又建了 `scripts/` | 二者重叠 —— 工程工具随线走（`engineering/`），**一个职能只留一个落点** |

## 第 4 步：动了目录，必须修链接

**如果差异清单里包含任何改名 / 移动目录**：

1. 先搜出所有引用（md 与 html 都要搜）
2. 逐个改正
3. **逐个实测可达**（`Test-Path`），断裂数必须为 0
4. **回读确认**（不能只信脚本的输出）

## 第 5 步：输出与执行（**审一次 → 一次改到位**）

- 把第 0 步那两张单子交给使用者**审一次** —— **整体批准（"都按建议改"）或圈掉若干条**都行
- **没有批准的部分，一条不动**
- **使用者拍板优于硬规则 —— 但必须写明「由使用者决定」＋代价**：使用者可以拍板**保留**不合硬规则的东西（命名 / 落点 / 结构），**以他的批复为准**，不再争；但**清单与本轮记录里必须留痕**：写明**「由使用者决定」**＋**代价**（会带来什么后果、以后谁会踩到），并在该项目 `AGENTS.md` §九 记一行。**只写"已批准"不写代价 ＝ 没完成** —— 下次会话的 Agent 只看得到结果、看不到这是例外，例外就会被当成"常规做法"继续复制
- 批复范围内**一次执行到位**（不摊成多轮）：动了目录就按第 4 步逐个修链接并实测，改完**回填一条评估记录**
- 记录落点：优先该项目**已有的进度文件**，没有才是 `MEMORY.md`

### 交使用者之前，先过一遍「对齐完成验收条件」（**六条，一条不能省**）

| # | 检查 | 判据 |
|---|---|---|
| 1 | **形态要求的件在不在** | **PRO 版**：`content/` ＋ `engineering/` ＋ `CONTRACT.md` **三样都在**；**标准版**：**没有** `content/` `engineering/`（有就是判错形态或没清干净） |
| 2 | **触发条件已满足却缺的目录** | 逐条对 `versions.md` §四 顺序表：**有东西装、却没目录 = 缺陷，要补** |
| 3 | **不该有的别硬建** | 没有对应产物的"按需"目录（`models/` `release/` `archive/` …）**不许为了"看着完整"新建空目录** —— **不预建仍是硬纪律** |
| 4 | **落点与命名** | 根目录**不放任何产物**；**骨架层**目录名英文小写、骨架文档英文大写 |
| 5 | **链接 ＋ 旧口径残留** | 动过目录 / 改过口径 → ① 按第 4 步**逐个实测可达，断裂数 0**，并回读确认；② **活文本里的旧口径关键词零残留** —— 把旧关键词（旧目录名 / 旧路径 / 已废止的说法）**全库 grep**，**逐处列出判定**：**在用旧说法 → 改**；**在声明它已废 → 留**；**历史归档（`notes/` 一类）除外**。**注释、命令行示例、脚本里的死路径也算**（链接检查查不出来 —— 一次真实试用里就漏了 3 处） |
| 6 | **`AGENTS.md` 三样都在** | 形态结论 ＋ 「产物长出来的顺序」表（**已建/待建如实标**）＋ 文档写入规范 |

> 六条过完才算"改到位"，然后交使用者检查；**任何一条没过，就还没完**。

## 不要做的事

- ❌ 没批准就改、没批准就建
- ❌ 拿「**内容被别的文档覆盖了**」当**删除已有文档**的理由（那是新建的判据，不是删除的判据）
- ❌ 顺手"规范化"使用者没点名的旧文件 / 历史命名（**没进清单或没被批准的一律不动**）
- ❌ 借整改之名做**全量重构**（改的是清单里批准的那些，别的照旧）
- ❌ 把批复的活摊成多轮慢慢改 —— **批准了就在本轮一次改到位**
- ❌ 为了对齐而预建空目录（**没内容就还是不建**）
- ❌ 项目已经在跑，却重走主流程（第 0–7 步）—— 走第 0.5 / 1 步（**没文档或只有一部分**时才到第 1.5 步）
