# 回头对齐 — 把已有项目拉到当前规范

> **仅在使用者明确要求时执行**（"把 X 项目按规范对齐"、"给这个项目补上规矩"）。
> 只是聊到文件夹结构时，不要启动本流程，也不要建任何文件。

**三个入口，同一套流程、同一个主出口：**

| 入口 | 重点 |
|---|---|
| **① 有规矩但过时 / 与实际做法对不上** | 比对差异、改结构 |
| **② 部分有规矩**（如已有 `AGENTS.md`，缺 `PRD.md`） | **只补缺的、不重写已有的**；目录命名差异照常进单子 |
| **③ 没规矩但有历史**（项目已在跑） | 从事实提炼规矩、补文档 |

> **入口①最常见的触发是 skill 自己升级了**（"项目要不要跟着对齐？"）—— 过时的不只是项目自己的规矩，
> 也包括它当初依据的 skill 版本。走法不新开，只把取证对象换成"版本差"：

| # | 步骤 | 产出 |
|---|---|---|
| 1 | **报版本号**：读 `SKILL.md` frontmatter，报现行版本 | — |
| 2 | **找项目记的旧版本**（常在 `AGENTS.md` / `PRD.md` / `MEMORY.md` 里）；**没记就如实说"没记"**，别猜 | — |
| 3 | **取版本差**：读 `references/changelog.md`，把「项目那版 → 现行版」之间每一行列出来 | 变更清单 |
| 4 | **逐条判影响**：有影响 → 说明影响哪份文件 / 哪条规矩；没影响 → 写「不适用」＋ 一句理由。**不许整段跳过** | 影响判定 |
| 5 | **出单子交批**：变更 ｜ 影响本项目吗 ｜ 影响什么 ｜ 建议怎么改；**「执行？」留白** | 差异清单 |
| 6 | **批了一次改到位** | 改动 ＋ 记录 |

> **判"无需对齐"是合法结论，但必须给证据** —— 逐条说明为什么无影响，不能只说一句"已符合现行规范"。
> **不许顺手升级**：这一轮只做"该不该跟"，改哪些由使用者批；没批之前一个文件都不动。
> **也不要在项目里写死"必须永远跟到最新版"** —— 跟不跟是使用者的决定。

**核心纪律四条：**

1. **规矩的权威来源是「已经发生的事实」，不是模板** —— 先看清楚实际怎么干活，再决定该写什么规矩。
2. **先只读，不动手** —— 产出两张单子，交使用者审一次。
3. **调用即整改** —— 主出口永远是「取证 → 清单 → 批准 → 改到位」；**没批准的部分一条不动**。
4. **动了目录就修链接** —— 所有相对链接改完必须逐个实测可达，并回读确认。

---

## 第 0 步：只读取证，出两张单子

**这一轮不许改任何文件。**

**① 事实清单 —— 这个项目实际上是怎么干活的？**

读目录结构、`git log`（谁在什么时候动了什么）、产出物、现有文档。写下：实际的工作流、约定的落点、
已经形成的惯例、明显踩过的坑，以及**线间接口 / 契约实际写在哪**。

> **先记一条「进场基线」**：进场时跑一次 `git status --short --ignored`，把输出原样记下来。
> 项目常驻的忽略项（`.trae/` `.workbuddy/` `.venv/` `dist/` `logs/` 这类）**进场就在，不是本次改动** ——
> 有了基线，跑完才能"只比差异"。

**② 差异清单 —— 现有文档 / 命名 / 目录和规范差在哪？**

| # | 项 | 现状 | 建议 | 影响面 | **判定** | 执行？ |
|---|---|---|---|---|---|---|

- **`影响面`**：若项目已对外分享，写清会不会断链 / 让旧链接失效；未分享就写「当前无外部链接」——
  **不要套一句在本项目里不成立的空话**。
- **`判定`**：执行方的建议判断 —— **缺陷** ／ **另一种合理选择（不改）** ／ **不适用**。进了单子就要给判定，理由可短但不能空。
- **`执行？`**：**留白**，由使用者在批复时填。**执行方不预填。**

> **必填列**：`项` / `现状` / `建议` / `影响面` / `判定` —— 少一列这张单子就没法审。
> **清单不是一次写完的**：第 0 步只立骨架，随第 0.5 / 1 / 1.5 / 2 / 3 步逐项补，第 5 步整张交审。
> 表可以按项目情况扩列 / 改分组，但**「判定」维度必须在** —— 既不禁止适配，也不许丢维度。

> ⚠️ **知情者偏差（先自查）**：若**你本人就是这个项目的长期参与者**，你的盘点会天然偏向「每项都不需要改」——
> 你看得懂，所以不觉得缺什么。此时必须额外问自己：**一个新人只读这些文档与 git 历史，接得上手吗？**
> 接不上 → 那是**缺陷**，不是"另一种合理选择"。

> **盘点不设范围上限**：读得越透越好 —— 发现「文档说的 ≠ 实际做的」是加分，不是越界。唯一护栏是**只读**＋**交审**。

## 第 0.5 步：先判「该不该动」，再谈「怎么动」

**盘点完了，不要直接进入"改"。先对每一项回答：这条差异是「缺陷」，还是「另一种合理选择」？**

| 判定 | 处理 |
|---|---|
| **缺陷** —— 会造成实际损害（断链、规则打架、误导后来者） | 进入后面的流程 |
| **另一种合理选择** —— 只是和模板不一样，但自洽且能用 | **明确写「本项判定不需要改」并给理由，同样算完成** |

**判断提示 —— 看规矩的来源**：项目自己长出来的（做法先成型、后成文）→ 差异多半是「另一种合理选择」；
外来模板套上的（先有模板、再要求现实符合它）→ 差异多半是「缺陷」。这只是**先验**，不是结论。

> ⚠️ **两类不适用本表**（它们是硬规则，没有"另一种合理选择"）：
> ① **骨架层命名不合规**（成分表里的目录名是中文 / 同层中英混搭 / 数字前缀）→ **零豁免**，一律列缺陷、建议改英文；
> ② **产物放错地方**（根目录住着产物、由源生成的成品没进 `dist/`、`release/` 被 AI 代刷）→ 见 `versions.md` §八。
>
> **不在管辖内的**：骨架目录内部的子目录与文件结构 —— 由项目自己定，**不列缺陷**（只可作建议）。

**这一步对「补」同样适用**：项目缺某份文档，也先问「缺了它，实际造成损害了吗？」
若项目已自行长出等效机制，**判定「不需要补」同样算完成**。

> ⚠️ **唯一例外是 `PRD.md`** —— 它承担「变更的比较基准」这一职能，别的文档替代不了。
> 缺 PRD 的项目，**判定是"要补"**，只是补法用历史反推（第 1.5 步）。

> **差异清单为空**只是「这个项目本来合规」的如实陈述，**不是流程的设计目标**。
> 流程**不会为了"改点什么"而制造改动** —— 该改的改到位，不该改的写明理由，两者都要留痕。

### 判断与事实要分开报

| 要报的东西 | 怎么核 |
|---|---|
| **判定**（要不要改） | 是结论，不由某条命令"证明"，但**必须给理由** |
| **事实：无跟踪文件被改** | `git status --short` 里**除 `??` 外任何状态位非空都算被改**：`M` / `A` / `D` / `R` / `C` / `U` / `T` 都算 —— **只看 ` M` 会漏判已暂存的 `M ` `MM` `A ` 与改名 `R `** |
| **事实：无未登记的增删改** | `git status --short --ignored`（**必须带 `--ignored`**），**与进场基线逐行对照、只比差异** |

> ⚠️ **别指望这条输出"完全为空"** —— 常驻忽略目录进场就在。判据是**与基线有无差异**，不是"输出是否为空"。
> ⚠️ **不许用 `git diff --stat` 去"实证没有改动"** —— 它看不见未跟踪文件，证不了"没有新增"。

## 第 1 步：骨架文档齐不齐

| 应有 | 检查什么 |
|---|---|
| `AGENTS.md` | 是否存在；是否含**「产物长出来的顺序」表**、**写入规范**与**领地声明** |
| `MEMORY.md` | 是否存在；是否按日期累积（最新在上） |
| `PRD.md` | 是否存在；是否含**「前提假设」**一节 |
| `ROADMAP.md` | 是否存在；是否有关卡与**当前唯一卡点** |
| `SOUL.md` | 是否存在；是否为协作准则（含协作方式节；按区并准则附录） |
| `USER.md` | 是否存在；是否含**项目默认根目录**（新建项目适用；已有固定位置的老项目可判「不适用」） |
| `ACCEPTANCE.md` | **只有进入验收前**才该有；早建即冗余 |
| 接口 / 契约 | 有没有线间接口？写在哪、**是否只写一处**、变更登记在哪（见 `versions.md` §九）—— 没有就判「不适用」 |

> **逐条给判定，不许跳过任何一行** —— 每条要么进"建议改"，要么写明「不需要改」或「不适用」并给理由。
> **默默跳过 ＝ 漏检**，而且事后看不出来是"判过了"还是"漏了"。交单子前**回数一遍行数**。

**判据分两用 —— 混用会误删文档：**

| 用在什么事上 | 判据 |
|---|---|
| 决定**该不该新写**一份 | 「它回答的问题，别的文档回答不了吗？」—— 回答得了就别新建 |
| 决定**已存在的要不要删 / 合并** | 「它承担的职能，别的文档承担得了吗？」—— **这是更高的门槛** |

> ⚠️ **不要拿前一条去删已有文档。** 「内容被别处覆盖」**不等于**「职能可以被替代」——
> 基准类文档尤其如此：基准的第一要求是单一、稳定、可对照，散在三处 = 没有基准。**`PRD.md` 默认不删、不并。**

## 第 1.5 步：没有骨架文档（或只有一部分）时 —— 是「补」，不是「改」

> **只补缺的文档，已有的不重写、不"顺便规范化"**。补哪几份由第 1 步逐条判定给出。
> **不要把主流程（第 1–7 步）重走一遍**，也不要从"建项目文件夹"开始重来。
> 走法：**从已发生的历史里反推规矩。**

1. **定领地**：这个项目实际有没有内容源、有没有工具脚本、有没有线间接口？
   代码放哪按角色归位（`src/` `tests/` / `engineering/`）。
   **同时先读 Agent 侧已有的全局约定**（全局自定义指令 / 全局配置）——
   已经写过的不要在这里再写一遍（例：全局已有完整编码准则，`SOUL.md` 就不必再并一份）。
2. **建议补哪几份，写进差异清单** —— 随整张单子一次交使用者批；批完一次写完，不要挤牙膏。
   > ⚠️ **批准的是「补哪几份」，不是「PRD 内容通过」** —— PRD 正文补完后**单独停一次**交审，审过才写 `ROADMAP.md`（见第 8 条）。
3. **按事实清单写 `AGENTS.md`**：把第 0 步看到的实际做法写下来 ＋ **一句话领地声明** ＋
   **「产物长出来的顺序」表**（从 `versions.md` §四 原样抄，已建标 `☑`、未建标 `☐`）＋ **文档写入规范**（§四，六条验收第 6 条要查它）。
   **不要写"我们希望以后怎么做"** —— 契约要对上现实。
4. 补 `MEMORY.md`（从 `git log` / 产出物回填关键决策与当前状态）、`USER.md`（现问）、
   `SOUL.md`（协作准则 ＋ 协作方式节 ＋ 按区并入准则附录）。
5. **补 `PRD.md` —— 用历史反推**：目标、硬性约束、**前提假设**、验收基准，从已经做过的事里提炼。
   > ⚠️ **"不用从零写" ≠ "不用写"。** PRD 是变更的比较基准，缺了它，往后所有改动都没有对照物。
   > 接口 / 契约也算 PRD 的职能域：把历史里实际在用的字段 / 格式约定写进 `PRD.md` 对应节，
   > 或独立成 `CONTRACT.md` ＋ `PRD.md` 留指针；**变更记录仍归 `PRD.md`**。
6. **已有等效机制就不要强改**（项目自带的入口文件 ＋ 进度文件 ＋ 记录已能顶事）—— **补差异，不改形状**。
7. **不重排目录** —— 补规矩不是趁机大扫除。但"不重排"≠"不许列入单子"：目录命名差异照常进单子，
   由使用者审一次、按批复一次改到位，动了目录就按第 4 步修链接。
8. `ROADMAP.md` 仍**等 PRD 正文审核通过**再写（清单批准 ≠ PRD 通过）；补完把结果回填一条到 `MEMORY.md`。

## 第 2 步：目录名与落点是否合规

> **先定目标结构，再谈名字** —— 先看清该有哪些区（按 §一 的触发条件，`engineering/` 有脚本才建、
> `content/` 有源才建、契约有线间接口才建），再谈名字。
> **命名只管骨架层**：成分表里的目录名用**英文小写**（`versions.md` §三.4）—— **硬规则，零豁免**。
> **骨架目录内部由项目自己定** —— 不看不列。

**中文目录名对号入座**（改名逐个来，改完同步 `AGENTS.md` §二 目录树与 §三 状态；**使用者拍板保留中文名的**，另在 §九 记一行「由使用者决定」＋代价）：

| 现状（中文名是事实，不是规范） | 规范 |
|---|---|
| `内容/` `内容区/` | `content/` |
| `工程/` `工程区/` | `engineering/` |
| `技能/` | `skills/` |
| `计划/` | `docs/plans/` |
| `发布/` | `release/` |
| `资料/` | `docs/references/` |
| `历史版本/` `旧版/` | `archive/`，或直接交给 git |
| `产出物/` `交付物/` | `docs/`（手写即交付）／ `dist/`（由源生成）／ `assets/` `models/` |

> **其他目录**：拿 `versions.md` §三 的成分表逐项对。**目录不是"按某个维度切出来"的** ——
> 而是从那一张表里按需长出来：**先在表里取，表里没有的才造词并登记**。

**真正该动的三类**（都指骨架层）：① 名字误导归属或造成混用（数字前缀、同层中英混搭、`产出物/` 这类指代不清）；
② 中文目录名（零豁免）；③ 内容确实该换落点（图件混在文档目录里之类）。

> **零豁免 ≠ 可以自行改名** —— 判定一律是"缺陷、建议改英文"，但**执行仍要使用者批**：逐项进单子，没批就不动。
> **唯一的出口在使用者手上**：他当轮拍板说"这个项目就用中文名" → 按他的决定记入 `AGENTS.md` §九，
> 并在单子上写明「**由使用者决定**」＋ 代价。

## 第 3 步：目录内容是否混放

| 检查 | 判据 |
|---|---|
| `models/` 与 `assets/` 是否混放 | 模型本体进 `models/`；被文档引用的图件进 `assets/`；一个文件只放一处 |
| `notes/` 里是否有本该进 `MEMORY.md` 的短结论 | 短结论（索引）进 `MEMORY.md`；长论证进 `notes/` |
| `notes/` 里两类文件是否混了 | 结论 `{任务名}_结论_{YYYYMMDD}.md` 可同主题续更；分析 `{YYYYMMDD}_{子主题}.md` 只增不改 |
| `logs/` 是否存在、临时文件是否乱落 | 临时文件一律进 `logs/`（已被 `.gitignore` 排除） |
| **根目录是否住着产物** | 根目录只住骨架文档、`README.md` 与 `.gitignore`；产物按 `versions.md` §八 落位 |
| `dist/` 的产物是否被手改、有没有生成入口 | 产物勿手改 —— 找不到生成入口的 `dist/` 文件 = 缺陷 |
| `release/` 是不是 AI 代复制 / 代刷新的 | 只由使用者手动从 `dist/` 复制定版；AI 不代劳 |
| 建了 `scripts/` | 该目录已退休（v1.2.0）：辅助脚本一律进 `engineering/` |

## 第 4 步：动了目录，必须修链接

1. 先搜出所有引用（md 与 html 都要搜）
2. 逐个改正
3. **逐个实测可达**，断裂数必须为 0
4. **回读确认**（不能只信脚本的输出）

## 第 5 步：输出与执行（**审一次 → 一次改到位**）

- 把第 0 步那两张单子交给使用者**审一次** —— 整体批准或圈掉若干条都行
- **没有批准的部分，一条不动**
- **使用者拍板优于硬规则 —— 但必须写明「由使用者决定」＋代价**：写明会带来什么后果、以后谁会踩到，
  并在该项目 `AGENTS.md` §九 记一行。**只写"已批准"不写代价 ＝ 没完成** ——
  下次会话的 Agent 只看得到结果、看不到这是例外，例外就会被当成"常规做法"继续复制。
- 批复范围内**一次执行到位**（不摊成多轮）：动了目录就按第 4 步逐个修链接并实测，改完**回填一条评估记录**。
- 记录落点：优先该项目已有的进度文件，没有才是 `MEMORY.md`。

### 交使用者之前，先过一遍六条验收（**一条不能省**）

| # | 检查 | 判据 |
|---|---|---|
| 1 | **按需规则在位** | 该建的建了、**不该建的空目录一个没有**；没有 `scripts/`（已退休） |
| 2 | **触发条件已满足却缺的** | 逐条对 `versions.md` §四：**有东西装、却没目录 = 缺陷，要补** |
| 3 | **不为"看着完整"硬建** | 没有对应产物的按需目录（`models/` `release/` `archive/` …）不许新建 |
| 4 | **落点与命名** | 根目录不放产物；骨架层目录名英文小写、骨架文档英文大写 |
| 5 | **链接 ＋ 旧口径残留** | 动过目录 → 逐个实测可达、断裂数 0；改过口径 → **活文本旧口径关键词零残留**（全库 grep，逐处判"在用旧说法 → 改 / 在声明它已废 → 留"，历史归档除外；**注释、命令行示例、脚本里的死路径也算**） |
| 6 | **`AGENTS.md` 三样都在** | 领地声明 ＋ 「产物长出来的顺序」表（已建/待建如实标）＋ 文档写入规范 |

## 不要做的事

- ❌ 没批准就改、没批准就建
- ❌ 拿「内容被别的文档覆盖了」当**删除已有文档**的理由（那是新建的判据）
- ❌ 顺手"规范化"使用者没点名的旧文件 / 历史命名
- ❌ 借整改之名做**全量重构**（改的是清单里批准的那些）
- ❌ 把批复的活摊成多轮慢慢改 —— 批准了就在本轮一次改到位
- ❌ 为了对齐而预建空目录
- ❌ 项目已经在跑，却重走主流程（第 1–7 步）
