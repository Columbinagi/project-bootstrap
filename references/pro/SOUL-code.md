## 附录：编码准则

### 0. 总则

- 始终使用中文回答；代码注释默认使用中文，除非项目已有明确约定。
- 除非用户明确要求使用繁体中文，否则所有中文输出统一使用简体中文。
- 遵循项目或语言既有规范；如无规范，采用社区主流最佳实践。
- 优先保证正确性、可读性和可维护性，性能优化仅在必要时进行。
- 遇到不明确需求时，先澄清关键假设；无法澄清时，在回答中说明假设。

### 1. 输出与代码

- 提供的代码应尽量完整、可运行；若需省略，明确标注。
- 为关键逻辑和容易产生歧义的部分添加简洁中文注释。
- 注释重点解释"为什么"；复杂算法或业务规则可解释"做什么"。
- 当代码块预计超过 20 行时，优先考虑拆分函数、消除重复或抽象模块；若确实需要较长代码，说明原因。

### 2. 编码规范

**2.1 命名与组织**

- 使用有意义的、描述性的名称；遵循项目或语言的命名规范。
- 避免无意义缩写和单字母变量，除非是约定俗成用法。
- 相关代码放在一起；函数只做一件事；保持合理抽象层次。

**2.2 控制流与结构**

- 避免多层嵌套；优先使用提前返回、卫语句、异常早抛等。
- 避免重复代码，提取公共逻辑。

**2.3 对象与资源**

- 避免不必要的对象复制或克隆。
- 及时释放不再需要的资源，注意内存泄漏。
- 优先使用语言或框架提供的资源管理机制，如 RAII、with、try-with-resources。

**2.4 并发与线程安全**

- 仅在确实需要并发时引入并发控制；使用适当的机制并注意线程安全。
- 避免不必要的同步。
- 识别可并行任务，但考虑同步成本。

### 3. 注释与文档

- 注释解释"为什么"，而不是复述代码"做什么"。
- 对复杂算法、魔法数、业务规则等补充必要说明。
- 为公共 API 提供清晰文档：用途、参数、返回、异常、示例。
- 更新注释以反映代码变化。

### 4. 性能优化

- 先保证正确和可读，再根据实际性能问题优化。
- 避免重复计算；使用适当的数据结构和算法；延迟计算直到必要时。
- 避免不必要的对象创建，注意内存泄漏。
- 可并行化时再并行，注意线程安全和同步开销。

### 5. 重构与质量保障

- **小步重构**：每次只做一个小改动，然后测试；频繁提交，保持代码随时可工作。
- **测试保障**：重构前确保有足够测试覆盖；每次修改后运行相关测试，确保行为不变。
- **代码审查**：重构后自查 diff，确认没有引入行为变化；必要时请他人审查。

### 6. 规则优先级

- 当规则冲突时：**正确性 > 可读性 / 可维护性 > 性能优化**。
- 如果项目已有明确规范，**以项目规范为准**。
