# 形态与落地清单 — 标准版 / PRO 版

> 本文件是 `project-bootstrap` 的**落地清单**：判定形态后照此执行。
> 判定只有**一道题** —— **这个项目是不是「双主业」？**（见 §一）
> 目录只有**一张成分表** —— 从 §三 里**按需生长**，不预建。

---

## 一、一道判定题：标准版 / PRO 版

> **判据只有一道题，与人员分工无关**：
> **这个项目是不是「双主业」——既有一条持续积累的内容源（词条、数据、文档源），
> 又有一条自己长期维护的、加工这些源的工程工具（引擎 / 流水线），两者靠一份格式契约衔接？**

| 答案 | 形态 | 落什么 |
|---|---|---|
| **是** | **PRO 版**（多线） | `content/` ＋ `engineering/` 两个**领地目录** ＋ `CONTRACT.md`（冻结两线接口） |
| **不是**（只有一类主业，工具只是零星辅助、用完不持续演进） | **标准版**（单线） | 骨架文档 ＋ 规范目录**按需生长**；**不分线** |

**为什么一道题就够**：PRO 版比标准版多的三样东西，全是「双主业」的必然结果 ——
两份主业各要一个家（`content/` `engineering/`）；两条线各自演进，接口不冻结就会对不上（`CONTRACT.md`）。
**人员分工不影响判定**：同一个 Agent 全包，只要项目是双主业，就长 PRO 版的样子。

**版本不是终身制**：标准版项目哪天长出「持续更新的内容源 ＋ 配套加工管线」，就**重新答一次**、升 PRO 版
（结论变更写进 `AGENTS.md` §一；若影响验收基准，同时进 `PRD.md` 变更记录）。

**能自己判断就自己判断，判断不了才问** —— 并把这一问**合并进第 3 步的提问**，不要单独多问一轮。

### 一.1 代码放哪：**不算判定题**，按角色归位

Agent 看**代码角色**自判，不问使用者：

| 代码的角色 | 住哪 |
|---|---|
| 项目本体是软件（库 / 框架 / 应用源码） | `src/` ＋ `tests/` |
| 辅助脚本（拼合、批量加工这类零星工具） | `scripts/` |
| 工程线的工具（PRO 版） | `engineering/` —— 工具脚本全在这；**有它就不建 `scripts/`** |
| 不写代码 | 都不长 |

> ⚠️ **都在「根目录」**：`src/` `tests/` `scripts/` 是**根目录下的一级目录**，与 `content/` `engineering/` **平级** ——
> **不是 `engineering/` 的子目录**（`engineering/` 里只装工程工具）。**"项目本体是软件" ≠ "把源码塞进 `engineering/`"。**

> **一条线可以有「两层」**：**这条线产出的是软件本体** → 源码进**根目录的** `src/` ＋ `tests/`；
> 而它**自己的工具脚本**（构建 / 校验 / 拼合那一类）仍进 `engineering/` —— 两层不冲突。

> **测试与文档不是软件的专利**：任何项目都该有验收手段与写作 / 编码规范 ——
> **不再按"代码是产品还是工具"分两套待遇**（该判定已撤除）。
> **术语**（本文与 `SKILL.md` 统一）：**「工程线」＝「代码线」** —— 指**同一条线**；
> 它的领地是 `engineering/`；**若这条线产出的是软件本体**，源码进**根目录的** `src/` ＋ `tests/`
> （**与 `engineering/` 平级，不是它的子目录**），而它**自己的工具脚本仍进 `engineering/`**。
>
> **代码归位不影响形态判定**：内容项目里出现一个处理数据的小脚本，**不会**因此变成 PRO 版 ——
> PRO 版只认「**持续积累的内容源 ＋ 自维护的加工工具**」这两份主业。

### 一.2 三件事按线表述（多线项目逐线各写一遍）

| # | 事项 | 怎么写 |
|---|---|---|
| ① | **准则附录** | **按线并入** `SOUL.md`：内容线 → 《内容写作纪律》（`references/pro/SOUL-content.md`）；代码线 → 《编码准则》（代码是项目本体 → `references/pro/SOUL-code.md` **完整版**；只有辅助脚本 → `references/pro/SOUL-code-lite.md` **精简版**）。**几线就并几份，各管一条线**；**不要合并成一条** |
| ② | **授权范围（默认值）** | 内容线**不引入代码**、确需写脚本**先问**；代码线可自行写工具脚本 —— 口径写进 `AGENTS.md` §一。**它是默认值**：与 `USER.md` 冲突时**以 `USER.md` 为准** |
| ③ | **验收形态** | **按线各写** ＋ 一条**成品总验收**（各线都合格 ≠ 成品可用）。内容线：内容准确 ＋ 格式合规；代码线：测试通过 ＋ 行为符合规格；有流水线的：**产物可复现 / 与源一致**。**一律写成可被外部核对的判据**，不能写成「脚本跑通了」 |

> **形态结论的写法**（进 `AGENTS.md` §一）：
> `PRO 版（内容线 ＋ 工程线；改内容不得碰引擎）` —— 标准版项目就写一个值 `标准版`。
> **不要写成"双线型"**：那是形状名；形态要能回答"这个项目有没有两份主业"。

> **目录一律按需建**，不因形态预先创建 —— 见 §四 与 §三 成分表。

## 二、两种形态差在哪（**就三样，没有潜规则**）

| # | 差别 | 标准版 | PRO 版 |
|---|---|---|---|
| 1 | 内容源 | **不设领地目录** —— 内容按类型散在成分表目录里（文档成品 → `docs/`，过程记录 → `notes/`） | `content/` —— 一切「源」住这（**内部结构由项目自己定**，不照搬任何现有项目实例） |
| 2 | 工程工具 | 零星辅助脚本 → `scripts/`；项目本体是软件 → `src/` ＋ `tests/` | `engineering/` —— 工具脚本全在这；**有它就不建 `scripts/`** |
| 3 | 线间契约 | 无线间接口 → 无此件 | `CONTRACT.md` —— 冻结两线接口（不预建，但**产出依赖它的内容之前必须先定**，见 §十） |

> **其余一切相同**：骨架文档（§三.1 / §五）、目录成分表（§三.2）、命名规则、产物落点（§八）、
> 「不预建 / 按需生长」—— **两种形态不差待遇**。
>
> `src/` `tests/` **不是某一种形态的专属**：任何形态的项目，只要**项目本体是软件**就长它们（§一.1）。
> 跨线共享资产（`templates/` `skills/`）**不归任何一条线**，按需生长。

> **是否建目录，一律看"有没有东西装"** —— 成分表里的"什么时候长"列只表示**触发条件**，不等于"开工就建"。

> `CONTRACT.md`（线间接口 / 字段契约）**跟着「有没有线间接口」走，不跟着形态走** ——
> 但**双主业必然有线间接口**（判定题本身就含"两者靠一份格式契约衔接"），所以 **PRO 版一定有它**；
> 标准版通常判「不适用」。见 §三、§十。

## 三、目录成分表（**全库一张表；按需生长，不预建**）

> **行业主流目录名一字不改**（`docs/` `assets/` `notes/` `scripts/` `src/` `tests/` `dist/` …）。
> **先在表里取；表里没有的**才按用途造词（§六）。"什么时候长"列＝**触发条件**，不等于"开工就建"。

### 三.1 骨架文档（根目录；英文大写）

| 产物 | 干什么 | 放什么 · **边界判据** | 什么时候长 |
|---|---|---|---|
| `AGENTS.md` | **项目规则总纲**（每次自动加载） | 背景、**形态结论**、目录结构、**「产物长出来的顺序」表**、写入规范、命名、工作流 | 立项 |
| `MEMORY.md` | **进度记忆** | **结论与决策的索引** —— 简短、按日期、给 Agent 接手用（完整论证放 `notes/`） | 立项 |
| `USER.md` | **用户画像** | 偏好、雷区、提问偏好、**项目默认根目录** | 立项 |
| `SOUL.md` | **协作准则** | 角色、思维原则、纪律、反模式（＋**按线并入**的准则附录：内容线＝写作纪律 / 代码线＝编码准则） | 立项 |
| `PRD.md` | **需求基准** | 目标、约束、**前提假设**、验收基准、非目标、变更记录（见 §十） | 立项 |
| `ROADMAP.md` | **计划与关卡** | G1–G4 关卡、阶段表、当前卡点 | **PRD 经用户审核通过** |
| `CONTRACT.md` | **线间接口 / 字段契约** | 字段名、取值范围、编号规则、谁改谁不许改 —— **只在两线之间真有硬约束时才建**（不预建）；正文可独立成文件，**`PRD.md` 只放指针 ＋ 变更记录仍归 `PRD.md`**（见 §十） | 出现线间接口约定（PRO 版：**产出之前**就要定） |
| `ACCEPTANCE.md` | **验收记录** | 逐条对 `PRD.md` 验收基准的**实测值** | 进入验收前 |
| `README.md` | **给人看的门面**（对外首页；**不是骨架文档**） | 这是什么 ／ 怎么装 ／ 怎么用 ／ **当前版本与更新** ／ 许可证；**项目规矩只有一处正文＝`AGENTS.md`，本文不抄规矩**（两处正文必然漂移，见 §十） | **按需**：**要分享 ／ 要上线 ／ 要给人看**（**不建不算缺陷**） |

> **根目录只住骨架文档、`README.md`（按需门面）与 `.gitignore`，不放任何产物** —— 产物一律按 §八 落位。

### 三.2 目录

| 产物 | 干什么 | 放什么 · **边界判据** | 什么时候长 |
|---|---|---|---|
| `content/` | **内容线领地** | 一切「源」：正文、规范、清单、配置（**内部结构由项目自己定**，不照搬任何现有项目实例） | **仅 PRO 版**，出现第一份内容源 |
| `engineering/` | **工程线领地** | 工具脚本：构建、校验、转换、拼合、本地服务 —— **有它就不建 `scripts/`** | **仅 PRO 版**，出现第一个工程工具 |
| `src/` `tests/` | 主要源代码 / 测试（**根目录一级目录**，与 `content/` `engineering/` 平级） | **项目本体是软件**才长；多线项目里就是代码线的领地 | 出现第一份对应产物 |
| `scripts/` | 辅助脚本 | **辅助脚本代码**（没有 `engineering/` 时才用它） | 出现第一份零星工具脚本 |
| `templates/` | 母版与模板 | **可派生**的模板类资产（引擎母版、样板页、模板文件） | 出现第一份模板类资产 |
| `skills/` | 技能 | 每个技能一个子目录（内含各自的 `SKILL.md`） | 出现第一个技能 |
| `docs/` | 手写即交付的文档成品 | 报告、说明书、参考 —— **不是由流水线生成的**；**默认单文件 HTML**（`USER.md` 另有偏好从其偏好），md / PDF 亦可 | 出现第一份文档类交付物 |
| `docs/plans/` | 实施计划 | 一次性、**带日期**的计划文件 | 出现第一份计划 |
| `docs/references/` | 参考资料 | 外部资料、快照 | 出现第一份参考资料 |
| `notes/` | 过程记录 | **两类**：任务结论（同主题续更，只追加）＋ 分析论证（只增不改）—— 见 `AGENTS.md` §四 | 出现第一份过程记录 |
| `assets/` | 图件与静态资源 | **被文档引用的图件**：SVG、图片、示意图、数据 | 出现第一份图件 |
| `models/` | 模型 | **三维 / 实体模型文件本体** | 出现第一份模型 |
| `dist/` | **由源生成的最终交付物** | 流水线产物（拼合出的站点、导出的报告、模型包）；**勿手改 —— 想改回源头改 `content/` 或 `src/` 与 `templates/`，重新生成** | 出现第一份流水线产物 |
| `release/` | **对外定版的快照** | 使用者**手动**从 `dist/` 复制：**默认同名不改**；**要标定版日期就只在文件名尾加 `_{YYYYMMDD}`**（不换名、不改扩展名）；**AI 不代复制、不代刷新**；**进版本库**（对外快照要留痕） | 需要对外发布时 |
| `archive/` | **退役区** | **不再维护、但仍需被人一眼翻到**的东西（见 §六 `archive` 与 git 的分工） | 出现第一件需退役但仍要翻到的 |
| `logs/` | 临时文件与运行记录 | **约定的垃圾区**，被 `.gitignore` 排除 | 首次产生临时文件 |

> **`docs/` 与 `dist/` 的判据**：**手写即交付** → `docs/`；**由源生成** → `dist/`（判据见 §八）。
> **`models/` 与 `assets/` 的判据**：模型**本体**进 `models/`；**被文档引用的图件**进 `assets/`。**一个文件只放一处。**
> **骨架目录的「内部」不管**：`content/` `engineering/` `docs/` 等**里面**怎么分子目录、用什么语言，**由项目自己定**（命名规则见本节；**怎么分有方向性指导，见 §三.3**）。

### 三.3 骨架目录「内部」怎么分：**方向性指导**（**不是硬规则**）

> **内部结构由项目自己定**（命名语言也不限）—— 下面**只是方向**：
> **不达标不算缺陷、不列差异清单**；违背它的代价是"越来越难找东西"，由项目自己权衡。

1. **一层一个维度**：同一层只按**一个**标准分（按类型 / 按主题 / 按阶段，选一个），别混着来。
2. **同类同处**：同一类东西**只放一处**；出现第二处，就是漂移的开始。
3. **能平铺就不分层**：一类东西还不到几件（≲ 5–7 个文件）时，**别急着建子目录**。
4. **深度 ≤ 2–3 层**：再深说明分类维度选错了 —— 换维度比再加一层好。
5. **看名知意**：名字要能让人猜到里面是什么；**不用 `1_` `2_` 数字前缀**，**不留 `misc/` `其他/` `temp/` 这类兜底目录**。
6. **同类同格式**：同一类文件用**同一种**命名格式（带不带日期 / 版本号，一类定一次）。
7. **命名语言随项目习惯，但同一层保持一致**（要么全中文、要么全英文，混着放最难认）——**这条同样只是方向**。
8. **两个特例（尽量遵守）**：`dist/` **里面别手工加层级**（生成器说了算）；`archive/` **保持搬进来时的原样**（重排过就翻不到了）。
9. **推荐**：把每个骨架目录"装什么 / 不装什么"写一句到 `AGENTS.md` §三 表的备注里 —— 一句话省掉后面无数次"这个放哪"。

> **`MEMORY.md` 与 `notes/` 的判据**：短结论（索引）进 `MEMORY.md`；长论证进 `notes/`。
> **`notes/` 内两类的判据**：**结论是活的**（→ 同主题续更，只追加）；**分析是死的**（→ 只增不改）。

> **命名规则 —— 只管「骨架层」**（**硬规则，零豁免**）：
> ① **成分表里的目录名**（`content/` `docs/` `dist/` …）用**英文小写**；② 根目录**骨架文档**用**英文大写**（`AGENTS.md`）；③ **同一层不出现中英混搭的目录名**（骨架层）。
> **骨架目录内部**（项目自己长出来的子目录与文件结构 —— `content/` 里怎么分、`docs/` 下怎么组织）→ **由项目自己定**：**中英文都不限**，不属命名规则管辖（**本表另有约定的产出命名除外**：交付文档、`notes/` 两类文件、模型 —— 见 §六）。
> **内容文件名**（**默认值**）：**中文 ＋ 日期**（`餐桌架设计方案_20261004.html`）；**已有文件不改名**。
> **命名上不设例外**：**骨架层**不合规的一律**列差异项、建议改英文**；**改不改由使用者批**（判定与执行口径见 `realign.md` 第 2 步）。

## 四、什么时候建 —— 「产物长出来的顺序」

## 七、文档变长了怎么办（**提示线，不是上限**）

> **本 skill 不设 KB 硬上限**，两条理由：
> ① **数字给不出依据** —— 为什么是 50K 而不是 60K？拿实测值倒推出来的阈值是自缚手脚；
> ② **会与「`MEMORY.md` 只追加、不覆盖旧条目」直接冲突** —— 迟早必须违反一条，
> 而能松的那条只有「只追加」，**等于变相逼着删历史**。
> **KB 是文件属性，不是文档质量问题。**

**触发（体感判据，不用数字）**：**找一条结论要滚超过 3 屏**，或**同一主题翻起来要来回跳**。

**记录类文件（`MEMORY.md` / `notes/`）：只搬迁，不删除** —— 判据是「**是否还影响当前决策**」，**不是"有多旧"**：

| 条目 | 处置 |
|---|---|
| **仍会影响下一步判断**的结论 | **留在主文件**（哪怕它很旧） |
| **已收口、只作溯源用**的事件记录 | **整段搬迁**到 `notes/`，主文件留**一行索引** |
| **已被推翻的旧决定** | **必须留在 `MEMORY.md`** ——「曾经错在哪」是**防复发**的信息，不该被挪走 |

> **搬迁落到哪里（此处易歧义，写死）**：**优先用项目已有的归档区**（如项目自己的 `项目归档.md`、
> 已有的 `archive/` 或历史文件）；**没有才新建 `notes/`**。
> **不要为了搬运而新建一个与既有归档区并行的目录** —— 那本身就是**第二处漂移源**。

**规则类文件（`AGENTS.md` / `SOUL.md`）另按一条**：废止的规则**不得裸留** ——
规则文件里留着一条已废止的规则，后来者会照着干。要么删（git 有历史），要么**就地标注「已废止 → 现行为 X」**。

> **判据是「是否还影响当前决策」，不是「有多旧」。**
>
> **搬迁 ≠ 删除**：「只追加」约束的是**内容不丢**，不是**位置不变** —— 这个区分才让它与「只追加」不再打架。
>
> **Agent 不擅自动手**：发现该分层了，**在回复里提请用户**，不要自己搬。
>
> 主文件的代价是**隐性**的：每次会话全量读入，**成本线性增长、收益次线性** —— 单条结论的信噪比会越来越低。

## 八、产物落点（**全项目只有一种放法**）

> 项目自己的 `AGENTS.md` 里，这一节的对应物叫「**归档决策树（产物放哪）**」—— 同一件事，两个标题。

| 落点 | 放什么 | 规矩 |
|---|---|---|
| **根目录** | 只住**骨架文档**、`README.md`（**按需门面**）与 `.gitignore` | **不放任何产物** |
| `docs/` | **手写即交付**的文档成品（报告 / 说明 / 参考） | 直接放 `docs/` 下，带日期命名；**不是由流水线生成的** |
| `dist/` | **由源生成的最终交付物**（流水线产物：拼合出的站点、导出的报告、模型包） | **勿手改** —— 想改回源头改 `content/` 或 `src/` 与 `templates/`，**重新生成**；默认不进版本库（可由源重生成） |
| `release/` | **使用者手动定版的对外快照** | **从 `dist/` 复制**、**默认同名不改**（要标日期就只在尾部加 `_{YYYYMMDD}`）；**AI 不代复制、不代刷新**；**进版本库** |

> **判据**：**由源生成 → `dist/`**（勿手改）；**手写即交付 → `docs/`**。
> **不要让产物和源在同一层无标记地平铺**，也**不要为了分享方便把产物留在根目录** ——
> 那只能靠人的记忆维持，迟早有人手改产物。
> 产物在 `dist/` 里的**文件名保持稳定、不改名**；改名 / 移位造成的断链由**一次性修链接**处理
> （见 `realign.md` 第 4 步）。

## 十、PRD 与 AGENTS 的分工（**PRD 不省**）

> **§九 已整节删除**（原「目录切分的两种范式」—— 切法维度已废止，见 §十一 变更记录）；编号**不留空号**是有意为之。

> 这两份文档**内容会重叠**（都涉及约束与红线），但**分工不同** —— 不是冲突。

| | 回答的问题 | 归属判据 |
|---|---|---|
| `PRD.md` | **做什么、做到什么算成**（目标 / 约束 / 前提假设 / 验收基准 / 非目标 / 变更记录） | **对「结果」的承诺** |
| `AGENTS.md` | **怎么干活**（协作纪律 / 目录约定 / 命名 / 写入规范 / 红线 / 工作流） | **对「过程」的约定** |

> ### 一句话判定线
> 这句话改动时，**需不需要登记变更记录？**
> **需要 → `PRD.md`；不需要 → `AGENTS.md`。**
>
> ⚠️ **不要用「会不会变」来分** —— 两边都会变。区别在**改动的含义**：
> 改 PRD = **需求变更**，要留痕、要同步受影响的产物；改 AGENTS = **规则调整**，不留痕。

> ### 两条规则不一致时，以谁为准（**写死**）
> **判定线优先** —— 上面的分工表只用于**对号入座**。
> 当一句话既像"约束"又像"红线"、按两条规则会得出**不同**归属时，**按判定线定**：
> **改动要留痕 → `PRD.md`**；不留痕 → `AGENTS.md`。
> 理由：**主题归类是描述，留痕需求是后果** —— 描述服从后果。

> ### 防漂移（**硬要求**）
> 同一句话**只在一处写正文**，另一处**只放指针**（"见 `PRD.md` C1"），**禁止复制**。
> 一旦同一句话写了两遍，两份就会各自漂移 —— 这就是**基准散落**的起点。
>
> **适用范围**：指**实质条款**（约束 / 前提假设 / 参数 / 验收判据）。
> 「任何改动先比对 `PRD.md`」这类**指针性提醒**不算正文 —— 它是纪律，写几遍都无妨。

> **重叠不等于冗余。** PRD 独有的职能是「**变更的比较基准**」：
> 若这个基准散落在 AGENTS / MEMORY / ROADMAP 里，**就等于没有基准** ——
> 那正是「改来改去却说不清为什么」的根源。
> 基准的第一要求是**单一、稳定、可对照**：散在三处，改设计时要去三处拼，
> 其中一份被单独更新就**静默漂移**，也再判断不出"这是新需求还是翻旧账"。
>
> **所以 PRD 不省。** 遇到内容重叠，解法是**把分工写清**（上表），**不是把 PRD 去掉**。

> ### 接口 / 契约归哪（**多线项目最要害的那份东西**）
>
> 接口 / 字段契约（内容写成什么格式、工程按什么格式读、谁不许私改）**不是第三种文档** ——
> 按本节判定线，它属于 **`PRD.md` 的职能域**：**改它要登记变更记录**（改实现不用）。
> 承认它，是因为它既不是"需求条目"也不是"过程约定"，却要被两条线反复引用。
>
> 落点两种，**正文只许写在一处**（防漂移）：

| 情形 | 落点 |
|---|---|
| 契约很短 / 与约束混在一起即可 | **`PRD.md`** 里独立成节（如「接口 / 字段契约」）**或并入 §五 已定案参数**——两者都行，选一处写正文 |
| 契约被**两条线反复引用**、篇幅独立 | 独立成 `CONTRACT.md`；**`PRD.md` 只放指针**，**变更记录仍归 `PRD.md`** |

> **冻结边界（写死）**：契约**冻结之后** ——
> **改实现（渲染层 / 工具）不算需求变更**；**改契约才算**，走 `PRD.md` §九 变更记录。
>
> **不预建，但先定**：只有真存在线间接口时才建这份东西 ——
> 但**一旦存在，必须在产出依赖它的内容之前定下来并冻结**。
> 目录可以后长，**接口不能后补**：先写一百条内容再改契约 ＝ 前面全部返工。
